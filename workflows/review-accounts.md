# 定期与事件复核（手动实验版）

用途：检查账号是否仍有必要、依赖与授权是否可靠、判断依据是否过期。采用 [review](../templates/review.md) 记录发现，通过 ID 引用 account、delegation、decision；字段及证据语义见[记录约定](../docs/RECORDS.md)。本流程不安装调度器，不自动提醒、登录、撤权、停订或注销。

## 触发与范围

建议起点为季度全面复核，合作结束、角色/所有权/恢复入口变化、委托到期、规则更新、续费前、项目停摆或异常访问时立即专项复核。这是用户可调整的管理建议，不是平台统一期限或合规认证；尚未约定日期时为 unknown，不擅自建立日历或定时任务。

先确认本次对象、相关文件、允许的读取与模型外发边界、验收人以及是否允许保存复核记录。框架改动时先比较约定与流程，再由用户决定是否更新记录；不自动迁移。每轮最多两个高影响问题。未授权写入时只输出检查建议和拟保存路径，连草案也不保存。

## 检查清单

| 主题 | 核查点与保留的缺口 |
|---|---|
| 目标与必要性 | 仍服务哪个目标、身份、项目？维护成本、重复账号、闲置状态、未交付内容/订单/售后承诺有哪些？不活跃不自动删除。 |
| 归属与责任 | 实际所有者、平台登记主体、管理者、最终负责/维护者是否分别有依据？品牌不同不推断产权不同；未知归属仍是 unknown。 |
| 公开关联 | 当前关联是否仍符合用户选择？拒绝不能被备注/别名绕过；商业推荐另列披露和规则核验项，不凭隐私偏好宣称可隐瞒利益关系。 |
| 关键能力 | 发布、授权、删除、结算等谁能做？角色定义是否有最新适用依据？与本地委托范围是否一致？ |
| 恢复与登录依赖 | 关键入口是否明确归属与恢复责任？是否有共享入口、循环恢复、单点故障？只检查非秘密元数据，不收验证码或恢复码，不据“有邮箱”宣布可恢复。 |
| 服务与费用依赖 | 域名、服务、结算、订阅续费与截止日、替代方案是否明确？只记录建议，不代续费或停订；变更入口前查范围内反向依赖。 |
| 临时委托与协作 | 到期/撤销是否停止本地使用？平台是否仍有残留直接或继承权限？批准、执行、验证、台账更新哪一步未闭环？ |
| 规则与证据 | 来源 URL/指针、适用平台/账号类型/地区/动作、生效与查阅日期、全文或摘要、质量及复核条件是否足够？过时、冲突、摘要或不适用不能支持当前许可。 |
| 数据边界 | 台账是否误入公开 Git/同步？模型、历史、长期记忆、备份和工具边界是否变化？不批量读取无关目录或秘密验证。 |

## 输出、确认与追踪

1. 分开列出已核查事实、建议和 unknown/未覆盖项，注明范围、日期与证据 ID。用户确认复核记录不等于把依据全部升为 verified。
2. 给发现排序并解释风险：例如权限残留/恢复入口不明优先，续费到期按实际期限，其次闲置优化；不以固定分数假装完成风险评估。
3. 每项行动记录责任人、截止日或触发条件、拟变更 ID/字段与所需批准。授权变更走[闭环流程](change-access.md)；关键归属/关联变化逐项确认，不借“做一次复核”全量获批。
4. 获准后只保存指定 review 与允许的变更；其他记录通过 links 引用，未获准仍留在对话。保留失败、延后与拒绝，明确哪些问题尚未解决。
5. 给出下次复核建议，等用户决定。完成这轮核查不等于问题已清零、平台已撤权或账号可以安全交接。

专项发现进入对应 P1 人工检查：[停用/交接/退出](exit-or-handoff.md)、[事件处置](respond-to-incident.md)、[发布与商业化](publish-and-commercialize.md)。沿用本次已批准边界；需要新增读取、写入或关键变更时重新确认，不因转入另一流程获得外部操作权，也不直接删历史或注销。

验收：范围可追溯、未知不被覆盖、关键变化有逐项确认、未完成事项有责任/期限或明确 unknown、没有外部动作和未经许可的写入。用[虚构验收集](../examples/acceptance-tests.md)验证，文档齐全不等于环境已通过。
